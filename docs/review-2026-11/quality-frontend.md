# ptyro review: code quality in the front ends, tests and tooling

Reviewed 2026-11-11 against `the review checkout` (branch `docs/review-2026-11`, v0.0.68). Read-only: nothing was built, run or modified, except `scripts/unwrap-ratchet.py` in check mode (reads files, writes nothing).

Line numbers are from that checkout. `app.rs` is 12,563 lines there (the brief said 12,616).

Confidence labels: **verified** = I read the code at the cited lines; **partial** = read one side, inferred the other; **unverified** = inferred from a grep or a pattern.

## Verdict

The code is disciplined at the small scale and under strain at the large scale. Error handling, CI hygiene, fuzzing and the web's DOM safety are better than most projects this size. The problems are structural:

- One TUI file holds the whole state machine and 5,100 lines of tests.
- The web client's protocol types are hand-written and already wrong in one place.
- Host-level logic lives in the CLI binary and is reached three different ways.
- The integration suite has 27 private copies of its harness and 182 sleeps.
- The design record is 818 KB and has started to drift from the code.

None of these is tracked in ROADMAP.md (I grepped for `app.rs` decomposition, generated types, nextest, refactor: no task).

## Findings

### TUI (`crates/ptyro-tui`)

**F-01 (high) `app.rs` is one 6,400-line `impl App` plus 5,100 lines of tests.** Verified.
- Evidence: `crates/ptyro-tui/src/app.rs:929` `impl App {` runs to line 7361 with 162 methods; `:7463` `mod tests {` runs to the end with 155 tests and 203 fns.
- The `App` struct (`:759-923`) has about 110 fields. Roughly 25 of them are "mode" flags or `Option<…>` sub-states that are mutually constraining but independent in the type: `overlay`, `inspector`, `orch`, `sets_view`, `chat_panel`, `chat_aside`, `first_run`, `pad_popup`, `drawer`, `kept`, `prefix`, `zoom`, `sidebar_zoom`, `focus`, `follow`, `revealing`, `after_add`, `context_hint`, `retry`, `setup_run`, `close_inspector_after`, `quitting`.
- Why it matters: every feature edits the same file, the legal combinations of modes are only written down in the order of `if`s in `on_key`, and the file costs a full crate recompile per edit.
- Direction: other modules already extend `App` with their own `impl App` blocks (`form.rs` has 7, `screens.rs` 3, `chats.rs`, `runs.rs`, `sets.rs`, `inspector.rs`, `pad.rs`, `shells.rs`, `about.rs`, `health.rs`). Finish that move mechanically: `app/replies.rs` (`handle_reply`), `app/commands.rs` (`run_command`), `app/input.rs` (`on_key`, `overlay_key`, `mouse_event`), `app/prompts.rs` (`prompt_done`, `picked`), and the tests beside the code they test. No behaviour change needed for the first pass.

**F-02 (high) Input routing is a priority ladder of booleans, repeated per view.** Verified.
- Evidence: `app.rs:2842-2990` `on_key`. The same block appears four times, for `orch` (`:2884`), `chat_panel` (`:2893`), `sets_view` (`:2905`) and `inspector` (`:2913`):
  `if self.keymap.is_prefix(key) { self.start_prefix(key); } else { self.orch_key(key); } return;`
- Who gets a key depends on the order of twelve `if`s over `first_run`, `overlay`, `pad_popup`, `orch`, `chat_panel`, `sets_view`, `inspector`, `prefix`, `focus`, copy mode, session state and chat view. `mouse_event` (`:6576`, 281 lines) and `full_view()` (`:2994`) re-encode the same precedence separately.
- Why it matters: adding a full-screen view means editing three ladders consistently. A missed one is a key or click reaching what is hidden underneath.
- Direction: one `enum Screen { Panes, Inspector(..), Runs(..), Sets(..), Chat(..) }` (there is already a `screens::Screen` for the kept layout) with one `key()`/`mouse()`/`draw()` dispatch, and overlays as a stack above it. The four `Option` fields then cannot be `Some` at once.

**F-03 (med) Actions are stringly typed and dispatched by a 696-line `match` on `&'static str`.** Verified.
- Evidence: `keymap.rs:535` `pub struct Command { pub action: &'static str, pub arg: Option<String> }`; `app.rs:3100-3795` `run_command` with about 100 string arms, some re-matching the same string inside the arm (`:3147-3170`: an outer arm for six `session.*` names, then an inner `match cmd.action` on the same six).
- The registry is three parallel tables keyed by the same strings: `keymap::ACTIONS`, `cli_actions::TEMPLATES`, and the `SUGGESTED` table at `app.rs:717` that maps CLI command text in error messages to actions.
- Why it matters: a typo in an arm is a silent no-op; nothing checks that every `ACTIONS` id has an arm (a test checks templates only, `cli_actions.rs:400`).
- Direction: an `Action` enum with `id()`/`from_id()` generated by one macro from the `ACTIONS` table, so the compiler enforces exhaustiveness. Keep the string ids for config and docs.

**F-04 (med) `handle_reply` is a 611-line match over `(Pending, Result<Reply>)` with 64 `Pending` variants.** Verified.
- Evidence: `app.rs:2100-2710`; `Pending` at `:486-633`.
- The continuation-tag design is sound (see "done well"), but all 64 continuations for every feature sit in one function, and a wrong pairing falls through to a catch-all.
- Direction: group by feature, as already done for the pad (`:2116-2121` delegates four variants to `pad_reply`). Do the same for chats (about 20 variants), worktrees, runs.

**F-05 (med) Three ways to do work off the UI thread, and some blocking calls on it.** Verified.
- Evidence: `app.rs:1322` (`request` spawns and posts `AppMsg::Reply`), `app.rs:5178` (`run_script` hand-rolls its own spawn with a two-request chain), `about.rs:23` and `health.rs:326` (spawn the ptyro binary itself and parse its JSON).
- Blocking in the event loop: `inspector.rs:841` `std::process::Command::new("git")` followed by output, `health.rs:518` `Command::new("tmux")`, `app.rs:2172` area `std::fs::write` of a chat export, `tab.rs:155`.
- Why it matters: a slow `git` (a large repo, a network filesystem) freezes the TUI. Unverified whether `inspector.rs:841` waits on the child; it reads `out`.
- Direction: route every subprocess through one helper that returns an `AppMsg`.

**F-06 (med) The TUI gets host facts by running its own binary and parsing JSON.** Verified.
- Evidence: `about.rs:23-30` runs `ptyro about --json`; `health.rs:326-335` runs `ptyro doctor --quick --json` and on any failure uses `unwrap_or_default()`, so a doctor that crashes shows as "no problems".
- 60-odd TUI actions are CLI commands run in a split through string templates (`cli_actions.rs:21`).
- See F-12 for the architectural side.

**F-07 (low) Overlay keys are hard-coded and bypass the keymap.** Verified.
- Evidence: `app.rs:5529-5560` (`KeyCode::Esc | KeyCode::Char { c: 'q' }`, `'j'`, `'k'`, `'d'`); 187 `KeyCode::Char { c: '…' }` literals across the crate (app.rs 70, settings.rs 42, copy.rs 39). `Table` has only `Prefix, Global, Nav, Chat, ChatList` (`keymap.rs:503`).
- Why it matters: AGENTS.md says every option is configurable; overlay, inspector, settings and copy-mode keys are not, and the help overlay can only list them by hand.

**F-08 (low) Draw mutates through `RefCell`/`Cell` for hit-testing.** Verified.
- Evidence: `app.rs:909-911` (`links`, `strip_hits`), `settings.rs:418` (`hits`), `chat.rs:28-42` (five cells); 14 `borrow_mut()` calls.
- `ui::draw(app: &App, …)` is otherwise pure, which is good. Direction: return a `Hits` value from `draw` and store it after the frame.

**F-09 (low) TUI unit tests share one fixed temp directory.** Verified path, unverified impact.
- Evidence: `app.rs:7486` `std::env::temp_dir().join("ptyro-tui-prompt-test")`, `about.rs:448` likewise. 155 tests run in parallel against the same `PTYRO_HOME`. Any test that saves a view or config races the others. Use `tempfile::tempdir()` per test.

**F-10 (low) Small duplicated helpers.** Verified.
- base64 is implemented six times: `ptyro-tui/src/lib.rs:418`, `ptyro-core/src/secret.rs:22`, `ptyro-daemon/src/notifier.rs:950`, `ptyro-term/src/sniff.rs:266`, `ptyro-testkit/src/fake_structured.rs:732`, `ptyro-testkit/src/fake_adapters.rs:1110`, plus `crates/ptyro/tests/m9.rs:817`.
- `human_bytes` twice (`ptyro-core/src/model.rs:630`, `ptyro-daemon/src/chats.rs:3027`); `shell_quote` twice (`ptyro-core/src/settings.rs:1102`, `ptyro-agents/src/profile.rs:340`).
- The tmux-wrapped OSC writer is copied in `lib.rs:393-398` and `:405-410`.

### CLI binary (`crates/ptyro`)

**F-11 (med) A broken config file silently becomes the defaults in 16 CLI paths.** Verified.
- Evidence: `Config::load(…).unwrap_or_default()` at `serve.rs:289`, `projects.rs:989`, `about.rs:138`, `backup.rs:135`, `pad.rs:110`, `agents.rs:446` and `:514`, `cli.rs:975`, `complete.rs:120` and others.
- Why it matters: `ptyro serve` with a TOML typo starts with default `[remote]` settings and says nothing. The unwrap ratchet (F-27) makes `unwrap_or_default` the path of least resistance: 205 uses in `crates/ptyro/src`, 157 in the TUI.
- Direction: one `ctx.config()` that returns the error (or prints one warning) and is used everywhere.

**F-12 (high) Host-level logic lives in the CLI crate and is reached three ways.** Verified.
- Evidence: `crates/ptyro/src/host.rs:74-455` is a 381-line `match op { "config.get" => …` with 40 string ops over untyped `serde_json::Value` arguments (`a[k].as_str()`), served at `POST /api/host`. Several ops shell back out to the binary (`host.rs:33` `cli(args)`), and `host.rs:354` parses that output with `unwrap_or_default()`.
- So the same capability (doctor, about, profiles, logins, integrations, config, service, backup, uninstall) is: a direct call in the CLI, a subprocess plus JSON parse in the TUI (F-06), and a string-op HTTP call in the web (`web/src/conn.ts:161` `host(op: string, args): Promise<any>`).
- Why it matters: there is no schema for these 40 ops on either side. The web's argument names and the Rust `a["name"]` lookups are kept in step by hand; a rename fails at runtime as "name is needed". With a remote daemon the TUI's subprocess runs on the client machine, not the daemon's (unverified whether that is intended for `doctor`; `health.rs:323` says the agent updates are the daemon's and asks it separately, which suggests the split is known).
- Direction: a `ptyro-host` library crate with typed request/response structs (serde), used by the CLI directly, by `serve` as the `/api/host` handler, and by the TUI in-process. That also gives F-14 something to generate from.

**F-13 (med) The CLI re-implements a daemon policy client-side.** Partial (CLI side read; daemon side located only).
- Evidence: `projects.rs:985-997` `start_after_setup` reads `worktrees.start_agents` from the client's own config file and `ProjectConfig::load(&info.root, &wt.path)` from the client's filesystem, then `wt new --agent` waits and spawns in separate requests (`:960-982`). `start_agents` is also handled in `ptyro-daemon/src/worktrees.rs` and `daemon.rs`. The TUI and web have no reference to it.
- Why it matters: with `--remote`, the paths are another machine's; and the three front ends can disagree about when the agent starts.

**F-14 (low) `--json` and printing are ad hoc per command.** Verified.
- Evidence: the identical function three times: `cs.rs:322` `json_out`, `orch.rs:277` `json_out`, `projects.rs:449` `print_json`; 71 direct `serde_json::to_string*` calls and about 130 `if json` branches across `crates/ptyro/src`. Long command functions follow from this: `cs.rs:465` `cs` 434 lines, `projects.rs:999` `wt` 401, `setup.rs:416` `update` 332, `chat.rs:457` `run` 309.
- Direction: handlers return a value implementing `Serialize + Display`; one place prints.

**F-15 (low) Test fakes ship in the release binary.** Verified.
- Evidence: `crates/ptyro/Cargo.toml` lists `ptyro-testkit` under `[dependencies]`; `main.rs:1421` `Cmd::FakeAgent` has no `cfg(debug_assertions)` (the other three fakes do). The doc comment says `doctor` uses it, so this is deliberate, but it links `fake_adapters.rs` (1,126 lines) and `fake_structured.rs` into release. Move only `fake_agent` out of the testkit if size matters.

**F-16 (low) A misplaced doc comment.** Verified. `main.rs:1383` "`123`, `#123` or a GitHub URL ending in the number" sits on `parse_access`; it belongs to `parse_number` at `:1394`. The TUI has a second parser for the same input (`app.rs:187` `work_source`).

### Web (`web/`)

**F-17 (high) Protocol types are hand-copied and one has already drifted.** Verified.
- Evidence: `web/src/data.ts:8` declares `RepoStatus { …; unstaged?: number; …; conflicted?: number; …; [k: string]: any }`. The Rust struct (`crates/ptyro-core/src/model.rs:118-148`) has `modified` and `conflicts`; there is no `unstaged` or `conflicted`. The code at `data.ts:147` reads `st.modified` and `st.conflicts`, which only type-checks because of the `[k: string]: any` index signature.
- `conn.ts:127` `request(req: object, timeoutMs): Promise<any>` and `conn.ts:161` `host(…): Promise<any>`: every reply in the app is `any` without the keyword appearing at the call site. The explicit count (169 `: any`/`as any`/`any[]`) understates it.
- Why it matters: `strict: true` in tsconfig gives little once every network value is `any`. A field renamed in Rust compiles cleanly in the web and shows as a blank cell.
- Direction: generate `web/src/proto.d.ts` from the Rust types (ts-rs or typeshare on `ptyro-protocol` and `ptyro-core::model`), a `make proto-types` target, and a CI diff check like `web-check`. Type `request` as `<R extends Request>(req: R): Promise<ReplyFor<R>>`.

**F-18 (med) The web client announces protocol 1.8; the daemon is at 1.39.** Verified.
- Evidence: `web/src/conn.ts:7` `export const PROTO = { major: 1, minor: 8 }`; `crates/ptyro-protocol/src/lib.rs:43` `minor: 39`. The web uses requests added long after 1.8 (chats are 1.22; `last_launch` at `data.ts:58`).
- Why it matters: version negotiation carries no information for web clients, so the daemon cannot shape replies for them. It works because `serve` and the app ship in one binary. A test pins 8 (`tests/m9.rs:188`).
- Direction: generate the constant with the types in F-17.

**F-19 (med) Hand-written sources live in the build-output directory.** Verified.
- Evidence: `web/dist/style.css` (39.6 KB), `index.html`, `manifest.webmanifest` and the icons exist only in `web/dist`; `web/src` holds only `.ts`. `scripts/web-check.sh` compares only `*.js`.
- Why it matters: "dist is generated, don't edit" is false for a third of it, and `rm -rf web/dist && make web` loses the stylesheet.
- Direction: move static files to `web/static/` and have `make web` copy them.

**F-20 (med) No package manifest, no lockfile, no linter or formatter for 10.7k lines of TypeScript.** Verified.
- Evidence: the compiler is `npx -y -p typescript@5.9.3 tsc`, pinned by string in two places (`Makefile:239` and `scripts/web-check.sh:6`). `.github/dependabot.yml` covers only `github-actions` and `cargo`. Every build or check downloads from npm with no integrity pin.
- Style is unchecked: 57 lines over 300 characters, the longest 636 (`data.ts:121` builds a whole document in one expression); `sessions.ts:355-356` are single-line objects of about 250 characters.
- Direction: a `web/package.json` with a lockfile (devDependencies only: typescript, and a formatter), `npm ci` in `make web`, and dependabot's `npm` ecosystem.

**F-21 (med) The service worker can mix app versions, which its own comment says it prevents.** Verified by reading; not reproduced.
- Evidence: `web/src/sw.ts:8-10`: "a flaky network can't give a page `app.js` from one version of ptyro and `settings.js` from another". But the fetch handler (`:66-74`) is network-first per request with a per-file fallback to the cached generation. After an upgrade, on a flaky link, `app.js` can arrive fresh while `settings.js` falls back to the old generation.
- Also `:44` picks the generation with `.sort().pop()` over hash-named caches, which is the lexically largest hash, not the newest; harmless only while `snapshot()` finishes deleting the others.
- Direction: decide per navigation, not per file: if `/` came from the network, serve modules from the network only (fail loudly); if `/` came from cache, serve everything from that generation.

**F-22 (low) The module list is maintained by hand in three places.** Verified; mitigated.
- Evidence: `crates/ptyro/src/serve.rs:61-110` (`js!("…")` per module), `web/src/sw.ts:13-16` (`FILES`), and `crates/ptyro/src/parity.rs:25-38` (`WEB_SOURCES`, 11 of the 28 modules). `web/test/assets.mjs` checks the first two against `web/dist`; nothing checks `WEB_SOURCES`, though a missing file fails safe ("action doesn't exist").
- Direction: a `build.rs` or `include_dir!` over `web/dist`, and generate `FILES`.

**F-23 (low) Terminal renderer: sound design, three avoidable per-frame costs.** Verified by reading; not measured.
- Evidence: `web/src/term.ts:164` calls `getComputedStyle(document.documentElement)` on every paint; `:228` assigns `ctx.font` (a string build and a font parse) for every non-blank cell; `:232` calls `fillText` per cell instead of per run of equal style.
- The rest is good: one `requestAnimationFrame` per burst (`:150`), rows redrawn only when their array identity or selection key changes (`:196`), paint statistics kept (`:203-208`).
- Direction: cache the two CSS colours and invalidate on theme change; set `ctx.font` only when the style id changes; batch runs.

**F-24 (low) Web view code is covered only by one browser test.** Verified.
- Evidence: the unit tests import only `kit`, `conn`, `data`, `screen`, `grid`, `keys`, `qr`, `pad`, `machine`, `cfgkit`, `chatkit`, `setupkit`, `shellkit` from `web/dist`. `settings.ts` (1,183), `chats.ts` (1,107), `panel.ts` (801), `app.ts` (728), `sessions.ts` (655), `projects.ts` (607), `runs.ts` (595), `notes.ts` (546), `review.ts` (277), `shells.ts` (241), `machines.ts` (113) and `sw.ts` (143) have no unit tests; `web/test/e2e.mjs` (435 lines, headless Chrome) is their only cover.
- The tests run against the committed `web/dist`, so editing `src` without `make web` tests stale code locally (CI's `web-check` catches it).
- Two web test scripts (`frames.mjs`, `pad.mjs`) run only from `crates/ptyro/tests/m9.rs:1196` and `:1224`, not from `make web-test`; `term.mjs` and `config.mjs` run from both.

### Tests

**F-25 (high) The integration harness is copied into 27 files.** Verified.
- Evidence: `struct World {` is defined 27 times under `crates/ptyro/tests/`; `const WAIT: Duration` 33 times with values of 10, 15, 20, 30, 40 and 45 seconds; `fn free_port` 4 times; `fn fake_ssh` 4; `fn git` 5; `fn http` 5; `async fn wait_for` 5; about 75 definitions of `ok`/`json`/`code`/`wait_screen`/`until` between them. `ptyro-testkit` provides `TempDaemon` but not the world around it.
- Each of the 53 files is its own test binary, so the workspace links 53 times.
- Why it matters: a fix to waiting or isolation has to be made 27 times, and the files have already diverged (six different timeouts).
- Direction: move `World` (home, fake agents on PATH, git helpers, `ok/json/code`, `wait_screen`, `until`) into `ptyro-testkit`, with one `WAIT` scaled by `PTYRO_TEST_TIME_SCALE`. Then fold the 53 binaries into a handful (`tests/it/main.rs` with modules) to cut link time.

**F-26 (high) Flakiness comes from fixed sleeps used as synchronisation, and from port picking.** Verified sites; cause-of-flake is inference.
- 182 `sleep(` calls in `crates/ptyro/tests`; most are poll intervals inside a deadline loop (fine). 34 are fixed waits of 400 ms or more that stand in for an event.
- Positive races (the test assumes something has happened by now):
  - `m6.rs:559-561`: `send "work 1.5 slow"`, sleep 500 ms, write `during.txt`, expecting the write to land inside a 1.5 s turn. Under load the turn may not have started, or may be over.
  - `m6.rs:391`: 1.5 s after "the first poll" before changing the fake `gh` data.
  - `m5.rs:282`: 500 ms before expecting "exited first".
  - `m5.rs:511`: 200 ms after a file appears before reading its content.
  - `shells.rs`: ten sleeps of 1.5 to 4.5 s (`:228`, `:315`, `:370`, `:389`, `:478`, `:480`, `:493`, `:496`, `:710`, `:742`).
- Negative checks (sleep, then assert nothing happened) pass vacuously when the machine is slow: `m9.rs:397` (400 ms, "read scope must not type"), `m9.rs:1536`.
- A TTL race: `m9.rs:482` sleeps 3.5 s for a pairing code to expire; the claim earlier in the same test must beat the same TTL (unverified what the TTL knob is set to).
- `free_port()` (`m9.rs:126`) binds port 0, drops the listener and returns the number: 15 call sites, each a window for another test binary to take the port.
- Fixed deadlines (`WAIT` 10 to 45 s) are not scaled by `PTYRO_TEST_TIME_SCALE`; only headless scripts are (`ptyro-testkit/src/headless.rs:138`).
- The owner's report (m9, m3, m6, m5 flake under load) matches: those files hold the largest share of these patterns, and each test starts a real daemon plus `ptyro serve`.
- The project's answer so far is a retry runner with a budget (`ptyro-testkit/src/bin/ptyro-flaky.rs`, `FLAKE_BUDGET ?= 2` at `Makefile:66`). It reports flakes honestly, but it re-implements what cargo-nextest does and budgets the symptom.
- Direction: replace the event-standing sleeps with waits on the event log or status (`ptyro wait`, `w.until`); have `serve` bind port 0 itself and report the port; scale every deadline by one knob.

**F-27 (low) The unwrap ratchet has two blind spots.** Verified.
- Evidence: `scripts/unwrap-ratchet.py:20` skips `ptyro-drive` as "test or development tooling", but `crates/ptyro-daemon/Cargo.toml:21` depends on it (it is the structured-session drivers) and its sources contain 7 `unwrap()`/`expect(` (not checked whether in tests). `:33` stops counting at the first `#[cfg(test)]` line in a file, and nine files have more than one (`ptyro-daemon/src/daemon.rs` 2, `engine.rs` 3, `ptyro-core/src/config.rs` 3), so code after a test-only helper is uncounted.
- The ratchet itself is a strength (34 in non-test code across the workspace). See F-11 for its side effect.

**F-28 (med) Tests are named by milestone, not by behaviour.** Verified.
- Evidence: `m2.rs` … `m11.rs`, `boot1.rs` … `boot8.rs`, `win1.rs` … `win11.rs`, `ux1.rs`, `ux2.rs`, `h2.rs`, `cfg1.rs`, `mm1.rs`, `note1.rs`. `m9.rs` (1,978 lines, 26 tests) covers pairing, device scopes, the WebSocket bridge, push, TLS and also runs the web app's Node tests (`:1196`, `:1224`, `:1480`, `:1728`).
- Test function names are good (sentences). The file names tell a newcomer nothing about where "worktree removal" is tested, and a failure reads `m3::…`.
- Direction: rename by area when folding binaries (F-25): `worktrees`, `profiles`, `remote_pairing`, `web_bridge`, `setup`, `windows_conpty`.

**F-29 (med) Large modules with no unit tests of their own.** Verified by count; whether integration tests cover them is not checked per function.
- See the table under Inventories. The heaviest in scope: `ptyro-tui/src/settings.rs` (2,941), `ptyro/src/projects.rs` (1,608), `orch.rs` (1,273), `uninstall.rs` (1,223), `cs.rs` (1,106), `ptyro-tui/src/runs.rs` (862), `profiles.rs` (621), `ship.rs` (612).
- The CLI command files are integration-only by design (366 integration tests spawn the binary). That is where the flaky suite's weight comes from: argument parsing and formatting that could be unit-tested are tested through a daemon.

### Tooling

**F-30 (med) `CHANGELOG.md` in the repository is 34 releases stale.** Verified.
- Evidence: the newest section is `## v0.0.34 (2026-10-30)` (`CHANGELOG.md:5`); the tree is v0.0.68 and `git tag` has v0.0.68. The file says "Generated … edit commit messages, not this file". The release workflow runs `make changelog dist` (`.github/workflows/release.yml:128`) on the runner and never commits the result.
- Direction: either stop committing it (generate into the release only) or regenerate it in `scripts/bump.sh`.

**F-31 (low) `make ci` is not what CI runs.** Verified.
- Evidence: `Makefile:149` `ci: check deny web-check web-e2e msrv fuzz-smoke installer-check ## Everything CI runs`. CI's `web` job runs `make web-check web-test` (`ci.yml:122`) and the macOS installer job runs `make brew-check` (`ci.yml:171`). `web-test` is in neither `check` nor `ci`.
- Related: `Makefile:300` describes `bump` as "…; then commit and tag", while `scripts/bump.sh:3` says "It doesn't commit or tag". `.PHONY` (`Makefile:36`) omits `spike-chat-meaning` and `icons`.

**F-32 (low) The parity checker proves a row exists, not that the feature does.** Verified.
- Evidence: `crates/ptyro/src/parity.rs:96-112` finds web actions by text search for `const ACTIONS = {` … `} as const;` in 11 hard-coded files and takes each line starting with `"`. It then checks that the first backticked word in a `docs/parity.md` cell is a known action id.
- It is a good consistency check for 350 lines of documentation and catches a new command with no row. It cannot tell that the action does what the command does, or that a new flag reached the TUI form. ## Five things done well

1. **Error discipline.** 34 `unwrap`/`expect` in non-test code across 200k lines, held by a ratchet in CI; zero `todo!`; one TODO comment in the repository.
2. **The web app's DOM safety.** No `innerHTML` anywhere; everything goes through `h()` (`web/src/kit.ts:9`) and `textContent`; a strict CSP (`serve.rs:113`); `localStorage` wrapped against throwing (`conn.ts:9`); pure logic split into `*kit.ts` modules so Node can test it without a browser.
3. **CI and supply chain.** Every action pinned by commit SHA, `persist-credentials: false`, `permissions: contents: read`, timeouts on every job, a five-platform matrix including WSL2 and native Windows, MSRV, cargo-deny, an SBOM, build provenance attestation, and an installer test on every push. CI calls only make targets.
4. **The TUI's update model.** `ui::draw(app: &App, …)` is read-only; background work returns as `AppMsg::Reply(Pending, Result)` where `Pending` names the continuation, so no callback captures `&mut App`; tests drive `overlay_key` and render to ratatui's `TestBackend` with no terminal. The shape is right; only its size is wrong.
5. **Fuzzing and the terminal layer's tests.** Eleven targets shared between cargo-fuzz and a stable mutation runner that CI runs, seed survival as a unit test, golden screen snapshots, property tests (deltas equal keyframes), criterion benches for parse and paint.

Also worth naming: the web bundle is checked against its sources in CI (`web-check`), and `web/test/assets.mjs` cross-checks the three file lists.

## The five refactors that would pay off most, in order

1. **Shared test world in `ptyro-testkit`, then fix the event-standing sleeps (F-25, F-26).** First because it is low risk, it makes every later refactor safer, and it addresses the flake the owner already feels. Move `World` and its helpers; one scaled `WAIT`; `serve` reports its own port; replace the 34 fixed waits. Then fold the 53 binaries into a few, named by behaviour (F-28).
2. **Generate the web's protocol types from Rust (F-17, F-18).** Mechanical once a generator is chosen; turns a class of silent runtime bugs into compile errors and removes the stale `PROTO`. Add `web/package.json` with a lockfile at the same time (F-20) and move static files out of `dist` (F-19).
3. **Split `app.rs` by moving code, not changing it (F-01, F-04).** Tests to their modules first (5,100 lines leave the file at once), then `replies`, `commands`, `input`, `prompts`. Do this before item 4 so the diff of item 4 is readable.
4. **Make screens and actions types (F-02, F-03).** A `Screen` enum with one key/mouse/draw dispatch replaces the three ladders; an `Action` enum replaces the string match. This is the change that prevents the next class of TUI bugs, and it is the riskiest, so it comes after 1 and 3.
5. **A typed `ptyro-host` crate behind `/api/host`, the CLI and the TUI (F-12, F-06, F-11, F-13).** Removes the 40 stringly ops, the TUI's subprocess-and-parse, and gives one `config()` that does not swallow errors. Largest in scope; do it once item 2's generator exists so the web side is generated too.

Cheap fixes that need no ordering: F-30 (changelog), F-31 (`make ci`), F-33 (`assert_cmd`), F-16, F-27, the SPEC corrections in F-35.
