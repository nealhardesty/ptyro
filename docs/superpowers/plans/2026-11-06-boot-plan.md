# BOOT — implementation plan

**Spec (binding):** `docs/superpowers/specs/2026-11-06-bootstrap-agents-design.md`.
**Roadmap:** `ROADMAP.md`, section "BOOT — Bootstrap: agents, tools and updates" (BOOT0–BOOT9).

Each task is one phase, one branch, and one PR stacked on the previous one. A task is done
only when its phase works as a whole: in the CLI, the TUI and the web where the phase has a
surface, tested, documented, and with CI green on its branch.

## Global constraints

These bind every task:

1. **AGENTS.md** is the rulebook:
   - **Parity:** CLI, TUI and web, with rows in `docs/parity.md`; `make parity` passes. The
     one exception: installs needing admin rights are TUI and CLI only, and the web shows the
     command, recorded as a waiver with that reason.
   - **Settings:** every config option gets its schema entry in
     `crates/ptyro-core/src/settings.rs` and appears in both settings screens.
   - **Make:** every runnable thing has a `make` target listed in the README.
   - **Database:** metadata only.
   - **Commits:** never add `Co-Authored-By` lines.
   - **Version:** do not run `make bump`; the last task does it once.
2. **SPEC.md, README.md, ROADMAP.md and RESEARCH.md stay true.**
   - Add or update the SPEC section for what the phase builds (a new §24 "Bootstrap", with a
     subsection per phase).
   - Add a README section for users.
   - Mark the ROADMAP BOOTn item built with a dated note, as other items are.
3. **The design's decisions are binding.** These are its "Decided" table and "My calls" (the
   owner can overrule my calls, but they are the plan until then). The "Left to the builder"
   items are the implementer's to decide; record what was decided in SPEC.
4. **Anti-goals hold everywhere:**
   - no admin, network install or update without the user's yes;
   - ptyro never reads or stores a credential;
   - a failure leaves the rest working, and offers the fix;
   - offline never blocks start-up;
   - no guessed install commands or versions (each comes from the BOOT0 table, dated and
     sourced).
5. **The network in tests:** never. Version lookups and installs are tested through fixtures,
   fakes and a debug-only test knob (`ptyro_core::test_knob`, `PTYRO_TEST_*`), as `fake-gh`
   is. No test installs real software or touches the developer's real package managers.
6. **Windows** is first class (SPEC §20.12):
   - Commands run without flashing windows.
   - Paths go through `ptyro_core::os` helpers (`canonicalize`, `slash_path`,
     `quoted_args`).
   - The code builds and passes clippy for `x86_64-pc-windows-msvc`: `make check-windows`, or
     `PATH="$PWD/scripts/xwin:$PATH" cargo xwin clippy --workspace --all-targets --target x86_64-pc-windows-msvc -- -D warnings`.
7. **Verification before a phase is done:**
   - `cargo fmt --all --check`, and `cargo clippy --workspace --all-targets -- -D warnings`;
   - the Windows clippy above;
   - `make test` (the flake-budget runner), `make parity`, and `make web-check` when the web
     changes;
   - then push the branch and confirm GitHub's CI is green on it (CI runs on every push).
     Use `gh run list --branch <b>`, then `gh run watch` or the API.
   - A red CI job is fixed before the phase is done. CI's Windows job takes up to about two
     hours.
8. **Git:**
   - Branch `bootN` from the previous task's branch. Push it with
     `git push -u origin bootN`.
   - Open the PR with `gh pr create --base <previous branch> --head bootN`. Its title starts
     "BOOTn:", and its body says what the phase does, how it was verified, and its open items.
     End the body with the line "🤖 Generated with [Claude Code](https://claude.com/claude-code)".
   - `gh pr edit` fails here; update a body with
     `gh api -X PATCH repos/nealhardesty/ptyro/pulls/<n> -f body=...`.
   - Never merge, and never push to master.

## Tasks

### Task 1: BOOT0 — the version table
Branch `boot0` from `boot-design`; PR base `boot-design`.
- Build the ROADMAP BOOT0 item: one verified row per agent and tool, and per platform (Linux,
  macOS, WSL, Windows x64/ARM64). Each row has:
  - the recommended install method and command, and how to update;
  - how to read the installed version, and where the latest version comes from;
  - the prerequisites, with their minimum versions;
  - the login command and how to confirm the login;
  - the vendor's documentation URL, and the date it was checked.
- Rows: Claude Code, Codex, Antigravity (`agy`), OpenCode, Gemini CLI (labelled for API-key and
  enterprise accounts), git, the GitHub CLI, Node.js.
- Check every value against the vendor's current docs on the web. Record each in RESEARCH
  segment G with a date and a [V]/[S]/[U] mark; a value you couldn't verify says so in the
  table.
- It lives as data plus a typed loader (a module, e.g. `ptyro-agents::catalog`), with unit
  tests and recorded fixtures for the latest-version sources (npm registry JSON, GitHub
  releases JSON, Claude's and Antigravity's feeds), parsed without the network.
- `install_hint` (`crates/ptyro-agents/src/locate.rs`) reads from it.

### Task 2: BOOT1 — the plan engine, `ptyro setup`, `ptyro install`
Branch `boot1` from `boot0`.
- Build the ROADMAP BOOT1 item and the design's goals 1–3 for the CLI:
  - the plan model (states, dependencies with prerequisites auto-ticked, elevation asked
    once);
  - running installs with live output, and a fix per failure;
  - the interactive `ptyro setup` checklist in a terminal;
  - `ptyro install <name>…`, and the unattended `--yes --agents … --tools …` form;
  - Node.js handled by the design's rule (the package manager when new enough, else the
    official build in a ptyro-managed folder on PATH through shell-init and the daemon's
    environment).
- It works before any daemon exists. It is exposed so the TUI and the web (later tasks) use
  the same engine: a library API, plus daemon requests (with a protocol version bump) for the
  web.
- Tests drive the whole flow through a fake installer (a test knob that runs scripted fakes
  instead of real installers).

### Task 3: BOOT8 — Windows: WSL, Windows, or both
Branch `boot8` from `boot1`.
- Build the ROADMAP BOOT8 item and design goal 4 in the engine and CLI:
  - per item, a WSL side, a Windows side, or both;
  - WSL detected as usable or not (WSL present, a distro, ptyro in the distro); never
    installed by ptyro;
  - without a usable WSL, the Windows side only;
  - the WSL side run through `wsl.exe` (or the WSL daemon), and both sides reported in one
    plan.
- Tested with fakes on every platform, and a Windows test in the CI `windows` job.

### Task 4: BOOT4 — logins
Branch `boot4` from `boot8`.
- Build the ROADMAP BOOT4 item and design goal 5 in the engine and CLI:
  - one account per agent and `gh`, through each tool's own flow;
  - run where the user sees a browser or device code;
  - confirmed by the tool's status command;
  - ptyro never reads or stores a credential;
  - setup ends by saying how to add accounts as profiles (`ptyro profile login`).
- Tested with fake tools.

### Task 5: BOOT2 — the TUI checklist
Branch `boot2` from `boot4`.
- Build the ROADMAP BOOT2 item: the checklist as the first part of the onboarding screen
  (`crates/ptyro-tui/src/onboard.rs`, UX1.19), on the engine. Everything the CLI does: ticks,
  sides, admin steps, live output, logins, the end-of-setup profile reminder.
- Reopened from `ptyro init`, the palette (`first.run`, and a `setup` action with a key or
  palette entry), and the health badge's fixes.
- Headless TUI tests (`ptyro_testkit::headless`, `send_when`/`until`, not fixed times).

### Task 6: BOOT3 — the web checklist
Branch `boot3` from `boot2`.
- Build the ROADMAP BOOT3 item:
  - the checklist under Settings, and a first-run banner when no agent is installed (web
    actions in `ACTIONS`, `web/src/app.ts`);
  - installs that need no admin run from the web;
  - admin steps show the command to run on the machine, and the TUI/CLI paths;
  - the parity waiver recorded in `docs/parity.md`, as the global constraints say.
- Rebuild `web/dist` (`make web`, committed). The web tests (`make web-test`, `make web-e2e`
  where a browser exists) cover it.

### Task 7: BOOT5 — out of date, offered
Branch `boot5` from `boot3`.
- Build the ROADMAP BOOT5 item and design goals 6 and 8:
  - daily checks remembered in `<state>/versions.json`, `doctor` checking afresh;
  - the finding with its one-step update and the command shown, in all four places: a
    start-up note once per new version, the TUI health badge, the web Health page, and
    `doctor`;
  - an agent in use when it updates (the design's call), and Windows' refusal to replace a
    running program, offered a retry;
  - `updates.check` and `updates.ignore` in the settings schema and both settings screens;
  - offline quiet.
- Tests with fixture registries and a clock test knob.

### Task 8: BOOT6 — ptyro updates itself
Branch `boot6` from `boot5`.
- Build the ROADMAP BOOT6 item and design goal 7:
  - the newer release found (GitHub releases), downloaded and verified with `SHA256SUMS`, and
    signed provenance where `gh` is present (as `scripts/install.sh` and `install.ps1` do);
  - then offered, in the same four places: install, then `daemon upgrade` live;
  - a package-managed ptyro (Homebrew) updated through its manager;
  - on Windows with WSL's daemon, both halves.
- Tested end to end against a local fake release server (no network), including a tampered
  download refused.

### Task 9: BOOT7 — moves to the recommended installer
Branch `boot7` from `boot6`.
- Build the ROADMAP BOOT7 item and design goal 9:
  - an agent installed another way detected (from its install path, as `locate.rs` knows npm
    shims, Homebrew and native installs);
  - offered the move to the table's recommended installer: install new, then remove old, with
    nothing lost (config and logins stay);
  - the offer can be dismissed per agent, after which it updates the way it is installed.
- In all three clients.

### Task 10: BOOT9 — the stale suggestions, then finish
Branch `boot9` from `boot7`.
- Build the ROADMAP BOOT9 item: every "no agent found" or "isn't installed" message
  (`doctor.rs`, `chats.rs`, `locate.rs` and any others) offers setup, and names Antigravity for
  Google.
- Then, for the whole feature:
  - the ROADMAP BOOT section's "Done when" checked where CI can check it, the rest listed as
    hand checks;
  - SPEC §24 complete, and the README section complete;
  - `make bump` once (the next patch version) in this branch.
