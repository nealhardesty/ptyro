## 0. Read this first

### 0.1 The verdict in one paragraph

The foundations are better than the pace of the project would predict: the PTY-to-client path, the
store, the local socket, the web server's security posture, panic discipline and CI are all
careful, and reviewers who went looking for a high-severity defect in the daemon's hot paths did
not find one. The weaknesses are all of one family: **the project is wider than it is deep, and it
checks that things exist rather than that they work.** 596 commits and 68 releases in 21 days have
produced 257 commands, about 200 settings, 50-odd concepts, and an orchestration layer with more
primitives than most competitors, which has only ever run against fake agents and which the
roadmap records as finished. The parity ledger passes while the TUI cannot unmute a session. The
agent guard reads as a boundary in SPEC and is a tripwire in code. The next stretch of work should
be about making what is already there true: real agents, real devices, real unattended runs, and
structural checks in place of ledgers.

### 0.3 What is genuinely good

A review that only lists faults misleads. These were named independently by more than one reviewer:

- **Panic and error discipline.** 34 `unwrap`/`expect` in non-test code across about 200k lines,
  held by a CI ratchet; zero in twelve crates. Poisoned locks are survived on purpose; a panicking
  request still answers its caller; the emulator is fed inside `catch_unwind`.
- **The PTY-to-client path.** The reader never waits for a writer; frames are damage-based,
  paced and acknowledged, so a slow client gets fewer, larger frames.
- **The store.** One owning thread, WAL, migrations in one transaction, a newer schema refused
  untouched, an older one copied aside first, and tests that migrate from every earlier version.
- **The outer security boundaries.** Socket directory 0700 with owner and peer-uid checks; 256-bit
  tokens hashed and compared in constant time; an exhaustive scope match with no catch-all; Host
  and Origin checks, a strict CSP and **zero `innerHTML`** in the web client; CA pinning between
  machines; actions pinned by SHA; `unsafe` confined to one crate.
- **Errors carry their fix,** and "never lose work" is real and worded the same in all three
  clients.
- **One settings schema** feeds the CLI, the TUI, the web and the docs, with a test that fails
  when a config field has no entry.
- **The TUI's update model** is the right shape (read-only draw, replies as named continuations);
  only its size is wrong.

### 0.4 How this was done, and how far to trust it

Eight reviewers worked in parallel on a clean checkout of `master`, one per lens (code quality was
split in two; one did industry research on the web). Several of them split their own reading
further. Each wrote a working paper with `path:line` evidence and an explicit list of what it did
not reach. The lead reviewer then read the papers and re-checked the headline claims against the
code.

**Nothing was built, run or tested** — the machine was shared with a live daemon and other work.
Every finding is from reading code. Each working paper labels its findings *verified* (the code
path was read end to end) or *suspected*; this document keeps those labels and adds "checked" where
the lead re-read the cited lines.

Lead spot-check results, 15 claims:

## 1. Usability

*How usable is this for an end user?* Full paper: [usability.md](review-2026-11/usability.md).

### 1.1 The first ten minutes

The paper walks a newcomer through install to first agent. The friction, in order: the README
leads with building from source and lists Rust as a requirement although the installer needs none;
it sends the user through `setup`, `init` and `doctor` and then says the first bare `ptyro` does
the same checklist; `init` asks about prefix keys and worktree locations before either word has
been explained; the quick start begins at line 387; the first thing on screen is a shell, not an
agent; a guessed command starts an agent (U-11); `--help` is 77 unsorted commands with lines up to
324 characters; putting it on a phone exposes it to the LAN with full scope and then needs a root
CA installed through five iOS settings screens. By minute ten the user has not yet met workspace,
profile, run, recipe, gate, change set, lease, radar, checkpoint, device scope or machine.

What works in those ten minutes: `ptyro "fix the flaky test"` is a good idea, the tour exists,
setup installs agents, and nothing the user did could lose work.

### 1.2 Findings by area

**Front door and concepts (U-01–U-10).** README is a reference manual where a front door should be
(high). Concept load is very high with no glossary outside SPEC §2.1 (high). Several things have
two or three names and several names mean two or three things: "pair" has three meanings, "remote"
two, `shell`/`shells` are different commands. Internal milestone ids leak into user-facing text.

**CLI (U-11–U-21).** Beyond U-11 and the flat help: singular and plural forms are sometimes aliases
and sometimes different commands; on/off is spelled six ways; time values three ways; some errors
leak internals; `completions` and `shell-init` name shells differently.

**Remote, update, recovery (U-20–U-26).** Version skew (see §0.2 #7). The major-mismatch message
recommends `daemon stop (sessions will end)` where the docs recommend `restart --hibernate`.
`backup` has no `restore`. "Quit ptyro" is one modifier from "detach".

**Configuration (U-27–U-31).** About 200 settings in 20 sections whose section and key names do
not line up; jargon in settings a reasonable user must edit; legacy options stay visible.

**TUI (T-01–T-24).** Four highs: the which-key menu needs 97 columns and at 80 cuts the column
holding detach, quit and "all keys"; with `NO_COLOR` mode badges are invisible and most list
selections have no marker; T-04 above; messages have one slot for 3–10 seconds and no history.
Mediums worth reading: a mouse click anywhere closes an overlay and discards what was typed; text
boxes can only append and backspace; Esc throws away a chat draft; `m` in the inspector's Checks
tab arms auto-merge with no question; forms do not scroll; the same letter does different things
after the prefix and in the sidebar; first-run Esc skips setup for good.

**Web (W-01–W-22).** Five highs, two of them accessibility: the config editor's textarea is
rebuilt on every app render so focus and caret are lost while typing (read, not run); expanded
diffs collapse on every re-render; many rows and all diff lines are click-only `div`s;
explanations live in `title` tooltips that a phone never shows; white text on mid-tone fills fails
contrast in the dark theme. Mediums: input typed while disconnected is dropped; an open tab never
learns the app was upgraded; sheets are not in browser history so Android's back gesture leaves
the page; a failed "new task" loses what was typed; a stray digit key starts a shell; leaving a
side chat deletes it without asking.

Already on ROADMAP: accessibility (H2.8), phone CA (H2.6, TS1.2).

### 1.3 Usability ideas

The paper has sixteen. The ones with the most leverage:

1. **`ptyro` is the only command a newcomer types.** No `setup`, `init` or `doctor` in the README;
   first run does the checklist, registers the repository and asks one question.
2. **A ten-command default help,** with `ptyro help all` and `ptyro help <topic>` for the rest.
3. **`ptyro help <word>` as a concept lookup:** one glossary feeds the CLI, the TUI's `?` and the web.
4. **Progressive disclosure by level.** `ui.level = basic | full` hides orchestration, change
   sets, leases, radar and machines from help, palette, which-key and web tabs until first use.
   The surface a new user meets drops by about two thirds without removing anything.
5. **Guess-safe CLI.** Unknown words never start an agent without a yes that shows the cost;
   `ptyro do "…"` as the explicit spelling.
6. **Self-healing version skew:** any client that sees an older daemon offers the live upgrade on
   the spot; the web shows "ptyro was upgraded: Reload".
7. **`ptyro phone`:** one wizard replaces `web on`, `config set remote.access`, `pair` and `devices`.
8. **Pair at `control` by default with in-app elevation** approved from the computer.
9. **A session "story" line:** one plain sentence per agent session that needs no vocabulary,
   reused for phone cards, notifications and a screen-reader text view.
10. **One-letter consistency as a test,** like the short-flag test: a letter bound in both the
    prefix and sidebar tables must run the same action or carry a waiver.
11. **README as a generated artefact,** with a doc test that fails when a table cell passes 100
    characters.

## 2. Code quality

*What has a bad smell?* Papers: [quality-backend.md](review-2026-11/quality-backend.md),
[quality-frontend.md](review-2026-11/quality-frontend.md).

### 2.1 Back end

No high-severity defect was found in the daemon's hot paths. The mediums:

| Id | Smell | Why it matters |
|---|---|---|
| Q-01 | Session events from the PTY reader carry an empty handle and `held: false`; the TUI replaces its whole row with them | Rows can lose their handle and held state until the next full update (likely, not reproduced) |
| Q-02 | `until_group_empty` polls every 250 ms with no bound; on Linux each poll scans all of `/proc` | One stuck process group costs CPU for ever |
| Q-03 | One task applies every session's signals and awaits git, scripts and notifications inline; its queue is unbounded and nothing restarts it after a panic | A slow hook for one session delays status for all |
| Q-04 | `chat.db` is migrated without the copy-aside that `ptyro.db` gets | The one database that holds user content has the weaker migration safety |
| Q-05 | git runs synchronously with no timeout, sometimes on async threads | A hung fetch holds a runtime worker, and holds a change set's job for ever (O-20.1) |
| Q-06 | The recorder (on by default) writes to disk on every PTY read while holding the terminal lock | Disk latency lands on the hot path |
| Q-07 | Requests are spawned without a per-connection limit and not cancelled on disconnect | A local client can queue unbounded work |
| Q-13 | `Daemon`: 78 fields, 46 mutexes, 42 `impl Daemon` blocks across files | Lock order and cleanup on session removal are not tractable |
| Q-14 | `Config` and the session list are deep-cloned on common paths | Quadratic listing |
| Q-15 | `ptyro-protocol` depends on `ptyro-agents` and `ptyro-run` for wire types | SPEC says it depends only on serde and core types so a WASM client can reuse it |

The second pass, over the orchestration-side daemon files, found the layer above the hot paths
thinner: change-set jobs that are memory-only across a restart (Q-22), incomplete rollback in
`cs new` (Q-23), `cs rm` ordering (Q-24), check-then-act across awaits with no per-set lock
(Q-25), a chat engine left running if `add_conv` fails after launch (Q-28), fire-and-forget chat
answer writes with fork/delete/compact as several separate transactions (Q-29), a command step
re-run beside itself after a live upgrade (Q-32), and machines that link only on identical version
strings (Q-36). The run engine itself — log, projection, gates, process-group cleanup — was judged
sound.

**An invariant to restate (Q-16, O-26).** "The database holds metadata, never contents" holds for
terminal contents. But `ptyro.db` does hold first-prompt titles, mail bodies up to 100,000
characters (diff hunks, contract diffs), review comments, notification text, and run event
payloads including `last_message` read off the screen and test output tails. Either the rule in
`AGENTS.md` needs a second named exception or these belong in files. See §9.

### 2.2 Front ends

| Id | Smell | Why it matters |
|---|---|---|
| F-01, F-02 | `app.rs`: one 6,400-line `impl App`, ~110 fields, ~25 mode flags, plus 5,100 lines of tests in the same file. Key routing is a 12-step `if` ladder with one block copied for four views | Every new view adds a rung; the key-meaning inconsistencies in §1 and §6 are the visible symptom |
| F-03, F-04 | `run_command` is a 696-line match on `&'static str`; `handle_reply` is 611 lines over 64 `Pending` variants | Stringly-typed actions cannot be checked against the keymap or the parity ledger |
| F-12, F-06 | `crates/ptyro/src/host.rs` is 40 stringly-typed JSON operations for the web; the TUI gets the same facts by running `ptyro about/doctor --json` and parsing | One piece of logic reached three ways, none typed |
| F-11 | 16 `Config::load(…).unwrap_or_default()` calls turn a broken config file into silent defaults, including in `serve.rs:289` | A typo in the config can change what `serve` binds to with no message |
| F-17, F-18, F-20 | Hand-copied protocol types, a stale `PROTO`, no `package.json`, lockfile, linter or formatter for 10.7k lines of TypeScript | §0.2 #9 |
| F-19 | `style.css` and `index.html` are hand-written inside `web/dist`, the build-output directory | Source and output share a folder |
| F-21 | The service worker can mix app versions, which its own comment says it prevents (`sw.ts:66`; read, not reproduced) | Half-upgraded web app after an update |
| F-13 | The CLI re-implements a daemon policy client-side (partly verified) | A second client that skips it gets different behaviour |

### 2.3 Tests, tooling, docs

- **F-25, F-26 (high).** §0.2 #10. The proposed first refactor in the whole review: one shared
  `World` in `ptyro-testkit`, one scaled `WAIT`, `serve` reporting its own port, and events in
  place of the 34 fixed waits.
- **F-28.** Tests are named by milestone (`m3.rs`, `ux1.rs`), not by behaviour; 53 test binaries.
- **F-29.** Large modules with no unit tests of their own (listed by size in the paper).
- **F-30.** `CHANGELOG.md` is 34 releases stale.
- **F-31.** `make ci` is not what CI runs.
- **F-33.** `assert_cmd` is declared and unused; test fakes ship in the release binary (F-15).
- **F-35.** SPEC.md is 818 KB in one file with lines over 1,000 characters. Of ten claims sampled,
  five were stale: the crate list (no `ptyro-meaning`), `gix`, the protocol crate's dependencies,
  the `Error` shape and codes, `assert_cmd`. `AGENTS.md` tells every agent to read SPEC before
  changing anything; at about 200k tokens it is read by grep, and the "[decided]" early sections
  are the ones that have drifted. ROADMAP is 269 done boxes to 19 open: mostly a completed-work log.

### 2.4 The refactors that would pay off most

Merged from both papers, in the order that keeps each step safe:

1. **Shared test world, then the sleeps** (F-25, F-26). Low risk, makes everything after it safer.
2. **Generate the web's protocol types from Rust** (F-17, F-18); add a package manifest and
   lockfile and move static sources out of `dist` in the same change (F-19, F-20).
3. **One subprocess runner** with a deadline, group kill, output cap and off-runtime execution,
   used for git, gh, secret commands and notifiers (Q-05).
4. **Split `app.rs` by moving code, not changing it** — tests to their modules first.
5. **Screens and actions become types:** a `Screen` enum with one key/mouse/draw dispatch; an
   `Action` enum in place of the string match (F-02, F-03). This is also the foundation for
   structural parity (§6.3).
6. **Break `Daemon` into subsystems that own their state,** as `Chats` already is (Q-13).
7. **The protocol crate owns the wire types** and is split by domain (Q-15).
8. **A typed `ptyro-host` crate** behind `/api/host`, the CLI and the TUI (F-12, F-06, F-11).
9. **Split SPEC by section** into `spec/NN-name.md` with an index, archive done ROADMAP items, and
   add cheap doc tests in the style of `parity.rs` (crate list, error codes, protocol version).

## 3. Missing features

*What could the future hold?* Full paper: [features.md](review-2026-11/features.md), with a
capability map, gap tables against tmux/zellij, modern terminals, remote tools and dev-environment
tools, and 74 ideas each with its CLI/TUI/web shape, size, the module it builds on, and its status
against ROADMAP and the RESEARCH funnel.

Caveat from the reviewer: ROADMAP's done tasks were read by milestone only, so an idea marked
"new" could be a sub-bullet of a done task. Check before promoting.

### 3.1 The observation that matters most

The idea funnel in `RESEARCH.md` Part III leans heavily toward orchestration (36 R-ORC rows) and
creation flows. Three everyday needs are thin or missing: **"what happened while I was away",
"find it again", and "get things in and out of a remote worktree".** Of the paper's top fifteen
ideas, eight are new to the funnel and three sit in the Backlog with no task id. They are mostly
small, and they are the ones that sharpen the product's wedge (§3.4).

### 3.2 Concrete gaps found in code

- OSC 8 hyperlinks are stored by the emulator and never rendered ("Our renderers never show
  hyperlinks", `emulator.rs:521`).
- Listening ports are detected and listed, never forwarded or opened.
- `backup` has no `restore`.
- OSC 133 command marks are already in the grid and used only as a status source.
- Only chats are searchable; terminal scrollback and recordings across sessions are not.
- PR features are `gh` only; no GitLab, Forgejo or Bitbucket.
- No chat attachments; no way to paste a screenshot into a remote agent.
- The outer-terminal matrix in `docs/compat.md` is entirely "—": untested by hand.
- No presence, share link, digest or snooze. Accessibility and i18n are stubs.

### 3.4 Identity

The sharpest wedge, in the reviewer's words: *the place where agents from any vendor, on any of
your machines and accounts, keep running and tell you truthfully when they need you.* What dilutes
it:

- **Chat.** Excellent, and the largest non-TUI subsystem. A general chat client with meaning
  search, imports and compare is a second product growing inside the first.
- **The three-clients rule at full strength.** A real differentiator that roughly triples the cost
  of every idea. Several good ideas are naturally one-surface (voice, native shells, a status-line
  feed). The current waiver test is too narrow for them (§9).
- **Windows depth before field proof elsewhere.** A native ConPTY daemon is built while the README
  says macOS has not been run by hand, the phone app has not been on a real phone, and three of
  five agents have not met the real thing.
- **Change sets and the merge train:** impressive, and far from the wedge for a single user.

## 4. Agent orchestration

*Still in its infancy — how do we make it better?* Full paper:
[orchestration.md](review-2026-11/orchestration.md).

### 4.1 Where it really stands

"Infancy" is right about maturity and wrong about surface area. In code today: an event-sourced
run engine with a pure planner, seven step kinds plus `loop`, four join modes, retries, three
timeouts, three budgets, typed outputs, gates, forks and restart recovery; fan-out with an
evidence-ranked compare; a mailbox with group addresses; file leases and a collision radar; lead
agents over a stdio MCP server under a daemon-enforced policy; multi-repo change sets with a
contract, write fences and a merge train; verified-done; per-turn checkpoints; a review queue. That
is more primitives than most products in `RESEARCH.md` Part I ship.

The infancy shows in five places:

1. **It has never run against real agents** (§0.2 #4).
2. **ROADMAP has no open orchestration task.** About twenty R-ORC rows are still `new`; five of
   them are marked `new` although largely built, which hides what is left.
3. **The happy path is built and the unattended path is not.** No stuck or loop detection, no
   handling of a step blocked on a permission prompt, no cost signal, no concurrency limit.
4. **Authority is uneven** (§0.2 #1).
5. **The user cannot see it.** A run is a list of step statuses: no timeline, no "why is this
   waiting", no cost, no cross-machine view, and no single list of what waits on the person.

### 4.2 Findings

**Correctness.** O-01–O-06 are in §0.2. Also: a run that fails or times out leaves its agents
running (O-08); every ready step starts at once and orchestrated spawns bypass the one throttle
that exists (O-09); no step has a default timeout, a `total` timeout restarts from zero after a
daemon restart, and retries have no backoff (O-13); nothing is ever cleaned up — worktrees, refs,
run directories (O-16); integrate and pick have no conflict ladder (O-24); the verify step and
`compare --refresh` share scratch directories without the same lock, and the judge reads
candidate-written diffs in a plain directory (O-25).

**Hollow primitives.** A recipe's `[policy]` table is parsed and never read (O-10).
`max_diff_lines` and `on_trip` are parsed only. `builtin:subtasks` has no consumer, so plan →
fan-out cannot be written as a recipe (O-12). Guards and leases are weaker than they read (O-11; detail withheld).

**Adapters (O-19).** Claude is first class; Codex is close but unverified on real turns;
everything else can be started and watched but not safely orchestrated. The paper's capability
table has a row per capability and a column per adapter. What it hides: a stale high-confidence
`working` never decays after one missed Stop hook; one adapter's tool denials are not wired
correctly and its tests pass because the fake differs from the real agent; a lead on an agent without MCP injection gets no tools and no message saying so; the
verified-done check may run 30 minutes while Claude's Stop hook gives up at 15.

**Front ends (O-22, O-23).** The web cannot list or run a repository's recipes (both requests send
`project: null`). A gate notification opens a session, not the run. Only permission prompts have
notification action buttons; gates have none. Recipe variable descriptions are dropped before they
reach a form. `claim` is exclusive by default over MCP and shared by default in the CLI.

**Reach (O-21).** Runs, gates, mail, leases and change sets are all local-only: another machine's
runs and gates are invisible, and no step can run elsewhere.

**SPEC against code (O-26).** A table of thirteen drifts, including "No silent shipping" (not
enforced for set members), the 4-hop mail limit, and the R-ORC-11 row marked built whose merge
ladder was not.

### 4.5 A staged path

The rule: **a run must be safe to leave alone before it is worth making smarter.**

1. **"It does what it says."** Canary runs against real agents (OI-01); fix O-01–O-08; default
   timeouts, teardown, a policy for every agent; `run why` and a reason line on every step; and
   reopen the area in ROADMAP so the document stops saying orchestration is finished. *Done when
   `overnight` and `implement-and-review` reach their gate on a real repository with the laptop
   closed and reopened, and the morning view explains each run in one sentence.*
2. **"Leave it alone, answer from anywhere."** The waiting queue with phone links for gates, then
   approval rules; the supervisor ladder with handoff; quiet workers and the digest; the full
   timeline, meters and the scheduler; delivery receipts and the notebook. *Done when a five-step
   recipe with a fan-out runs three hours, asks the phone twice, and the timeline shows where
   every minute went.*
3. **"The evidence pipeline."** Plan → expand → verify with conflict prediction; the tournament
   with decisive automatic selection, the review loop, holdout checks, model strategy; the merge
   queue; triggers; the selection log.

**Not to build:** a supervisor or router model inside the engine; more recipe language; a visual
workflow builder; free-form worker-to-worker chat; a vector memory; A2A or a dependency on MCP
Tasks; more adapters before the conformance matrix exists; ptyro's own cloud; more change-set
machinery until single-repo runs are solid; automatic *shipping* without a human by default.

## 5. Security

*What are we missing?* The full paper opens with a threat model — assets, eight actors, and a
table of which boundary the code enforces and which it assumes — and has 27 findings: **no
critical, 2 high, 11 medium, 14 low.** It is not in this repository (see the note in the header).
This section gives the shape.

### 5.1 The agent boundary is a tripwire

SPEC §17 states the model honestly — the boundary is the OS user — and the code's own comment
says the agent defaults "stop an agent's mistake or a casual prompt injection, not code set on
getting around them". The two high findings (S-01, S-02) are that the tripwire is much thinner
than SPEC's table of "refused to any agent" implies, in a way that needs no evasion, and that the
common default state is the open one. `SECURITY.md` lists this class of problem as in scope. A
casual prompt injection — a hostile README or web page read by an agent — is exactly the threat
that reaches this far, which is why they are rated high in spite of the stated model.

Direction: record that a session was started by an agent and treat it as one for guard purposes;
make an allow-list the default for every agent session and let policies widen it. This is the same
change as orchestration's OI-03. Three mediums sit beside it (S-03, S-04, S-13): a way around a
lead's policy, mail visibility wider than SPEC §17 states, and where one signing key lives.

### 5.2 Untrusted strings reaching a sink

Six findings (S-05, S-06, S-12, S-14, S-15, S-16; medium to low) where text from a child process,
a recording, an agent or a recipe reaches a terminal, a subprocess configuration, a shell line or
a recursive delete with less filtering than the surrounding code applies elsewhere. Each has a
small, local fix. Three were reasoned from source and should be confirmed by a test first.

### 5.3 Remote, machines, release

- **Pairing and the local CA** (S-07, S-08): how a pairing code is handed to a browser, and the
  breadth of what the certificate authority that phones are asked to trust could sign.
- **Machine links** (S-09): always full scope, with transitive trust between linked machines.
- **Audit** (S-10): device actions on the machine itself leave no record, though SPEC §17 says
  remote actions are in the event log.
- **Release integrity** (S-11): `SECURITY.md` overstates what the install script verifies.
- **Token lifecycle and defaults** (S-21, S-24): tokens never expire; default scope is `full`;
  the documented `web on` default without Tailscale is every interface.
- Lows: file modes narrower in SPEC than on disk (S-17), weaker file privacy on Windows (S-18),
  repository values outside the trust fingerprint (S-19).

### 5.4 Missing entirely

Controls that do not exist at all. None of this is news to an attacker; most of it is stated or
implied by SPEC §17.

1. Per-agent capabilities — one socket, one authority.
2. Provenance of sessions: nothing records that an agent started a session.
3. A tamper-evident audit log of who asked for what.
4. Sandboxing — documented, not built.
5. Secret redaction at rest: the scrubber is used only for summaries; recordings (on by default),
   scrollback, crash reports, inbox bodies and chat text are stored as seen.
6. Token lifecycle: expiry, idle timeout, rotation, new-address warning.
7. Narrow machine links and keychain storage.
8. A constrained CA.
9. A release signature that does not depend on `gh`.
10. Owner and mode checks on existing data directories at startup.
11. Fuzzing of several parsers that face untrusted input (the HTTP router, hook payloads, mail
    framing, command-line quoting).
12. One output sanitiser at the CLI print boundary.
13. Rate and resource limits for local clients.
14. **A `SECURITY.md` statement of the agent boundary as it really is,** so users know that
    "agents never answer for a person" is a default against mistakes, and what to do when they
    need more.

## 6. Inconsistency and parity

*What is not tracking across the application?* Full paper: [parity.md](review-2026-11/parity.md),
which includes the complete matrix of all 257 visible leaf commands against their TUI path and web
action, flag-level tables for every creating command, and verb, noun, key, confirmation and
status-colour tables.

### 6.1 The ledger passes; the drift is underneath it

Every command has a row in `docs/parity.md`, every first-named action exists, and there are no
`gap:` cells. `make parity` proves that an action *name* exists. It does not look at flags, and
most findings are a TUI or web path that hard-codes a request's optional fields.

**The TUI behind the CLI** — against "the CLI and the TUI are always in parity":
- Cannot unmute, or mute for anything but one hour (P-01).
- PR controls only switch on: no automerge off, watch off, or merge method (P-02).
- `wt integrate` takes no options (P-03).
- A gate note can only go with the first option (P-04).
- `pick` cannot apply files; only the CLI has `--hunk` or `--into` (P-05).
- 63 commands reach the TUI as the CLI run in a split; seven of those ask the user to type an id
  that is already on screen (P-07).
- `run events` has no TUI view; `usage` is one profile in the status bar (P-08, P-09).

**Missing from both UIs:** the mail ledger `msg ls`, whose row points at `inbox`, a different list
(P-10); backup options (P-11); assorted flags (P-12).

**The web behind:** its key-binding settings know three of five tables, so chat keys are
mishandled (P-14); the inbox is much thinner than the TUI's (P-15); it polls where the daemon
pushes (P-16); scratchpad Start does not link the item to its worktree (P-17).

**"Creating shows every option" fails in four places:** the TUI session form (no lead, no agent
arguments), the TUI new chat (no title, no workspace), the web fan-out (no profile), and in the CLI
itself, where `ptyro new` and `ptyro wt new` each lack half of the other's options (P-19–P-21).

**Config:** six kinds of key can only be edited in the file (P-22); the schema's ranges are
narrower than the parser's (P-23); the TUI cannot enter a multi-line script or prompt (P-24).

### 6.2 Behaviour and vocabulary

- **Confirmation differs by surface.** The CLI ends sessions, cancels runs and restores
  checkpoints without the question the TUI and web ask (P-27, P-44).
- **Colour means different things.** Blue is idle in the TUI and working on the web; the web gives
  idle and done one green (P-45).
- **Keys.** "Every key can be changed" holds for five tables only; overlay keys are hard-coded
  (P-30, F-07). Destructive keys change meaning by context (P-31). Digits mean different things in
  the TUI and the web; web keys are not rebindable and `docs/keys.md` has no web section (P-32).
- **CLI.** `--timeout` is a duration in some commands and bare seconds in others (P-34). The same
  status is `errored` and `error` in `--json`, and the doc names the wrong one (P-43). `ls`/`list`
  and `rm`/`delete` aliases are uneven (P-40). Two exit-code tables disagree (P-37).
- **Names.** Action ids and user-facing nouns differ between the TUI and the web, and inside each
  table (`*.remove` beside `chat.delete`, `review.rm`) (P-41). A message's `kind` depends on where
  it was sent from (P-28). Confirmation wording is shared in Rust and copied by hand in the web (P-29).
- **Docs.** `docs/cli-json.md` leaves out whole families that have `--json` (P-35);
  `docs/compat.md` never mentions Windows although the README makes `ptyro.exe` a main path (P-48);
  SPEC §11.3 is stale (P-38).
- **Platform.** `kill -s N` does nothing for most signals on a native Windows daemon (P-49);
  platform-specific settings show everywhere (P-50).

### 6.3 Making parity structural

The checker cannot see: flags and options; "hub" actions where one action name satisfies many rows
and the real path is a hard-coded key in prose (69 rows); an action that exists but does something
else; `shown:` and `waived:` cells (any text passes); web actions registered but used by no
control; reverse gaps (102 TUI-only and 138 web-only action ids have no row to live in); create
forms; rows that fail to parse (skipped silently); web modules outside a fixed list of eleven files.

Ideas, cheapest first:

1. **A field-level check.** For each `Request` variant, list the fields a TUI or web call site
   sets to a literal `None`, `false` or `[]` on every path, with waivers per field. A test could
   produce P-01–P-12 mechanically.
2. **Fail on a row that does not parse; check every backticked id; check that a web action is used.**
3. **Generate the web's request types from the protocol,** so a new field is a compile error at
   every call site (the same change as §2.4 item 2).
4. **Give reverse gaps a home:** a second table for TUI and web actions with no command.
5. **One operation registry.** Declare each operation once — id, request type, optional fields
   with label, kind and default — as `settings.rs` already does for config. clap args, the TUI
   form and the web form are generated from it or checked against it. A new optional field fails
   the build until each surface shows it or carries a waiver naming the field.
6. **Per-surface end-to-end tests over the registry:** drive each operation through the CLI, a
   headless TUI and the web harness and compare the request the daemon receives.

The settings schema is the proof that this works here: it is the one area where all three clients
and the docs agree, because there is one source.

## 7. Themes that cut across the lenses

Six observations that no single paper states, because each is visible only across papers.

**1. Existence is checked; behaviour is not.** The parity ledger checks that an action name
exists. Orchestration tests check that fake agents behave as the fakes were written, and at least
one adapter defect passes its tests for exactly that reason. SPEC is
"[decided]" and half its sampled claims are stale. The web's types are asserted by hand. In each
case the remedy is the same shape: generate from one source, or test against the real thing.

**2. One root cause, three papers.** The thin agent rules appear as S-01/S-02 in security, O-07 in
orchestration and behind one usability finding. Recording which sessions an agent started, plus a
default policy for every agent, closes all three, and is also the precondition for letting agents
spawn agents safely at all.

**3. The unattended path is the product, and it is the unbuilt part.** The pitch is many agents
running while you are away. The findings that block exactly that: wall budgets against gate time,
blocked steps that look like work, mail that is lost, no single waiting queue, no digest, no cost,
gates without phone links, no stuck detection. Features (the digest, snooze, catch-me-up) and
orchestration (the waiting queue, the supervisor ladder) arrived at the same list from opposite
ends.

**4. Width is itself the usability problem.** 77 top-level commands, 257 leaves, about 200
settings, 50-odd concepts, five key tables, three clients. No single item is wrong; the sum is
what a newcomer meets. Progressive disclosure (§1.3 #4) is the only idea on the list that reduces
it without removing anything.

**5. Version skew has no owner.** It shows up as a serde error on the CLI, a stale `PROTO` and a
"Forget this pairing" button on the web, a service worker that can mix versions, a command step
re-run after a live upgrade, and machines that refuse to link across patch versions. Each client
solved (or did not solve) it alone. With 68 releases in 21 days and a self-updater, skew is the
normal state.

**6. "Built" and "works" have separated.** macOS not run by hand; the phone app not on a real
phone; three of five agents never met; the terminal matrix empty; Windows hand checks open;
orchestration on fakes only. The cheapest valuable work available is a week of real-device and
real-agent use with a checklist that the tool itself fills in (OI-01, M-74).

## 9. Decisions only the owner can make

1. **Is the agent guard meant to be a boundary or a tripwire?** If a tripwire, SPEC §17's table
   and `SECURITY.md` should say so in the first paragraph, and S-01/S-02 become documentation
   work plus the cheap additions to the refusal list. If a boundary, it needs provenance and a
   default-deny policy, and the same work unlocks safe agent-spawned agents.
2. **Should bare multi-word input start a task?** It is the product's best first-run idea and its
   sharpest foot-gun. Options: keep and confirm when the first word resembles a command; confirm
   always; or require `ptyro do "…"`.
3. **What should `ptyro web on` do without Tailscale, and what scope should pairing default to?**
   Today: every interface, `full`.
4. **"The database holds metadata, never contents."** Mail bodies, review comments, run event
   payloads and `last_message` are in `ptyro.db` today. Name a second exception, or move them.
5. **The three-clients rule and one-surface features.** Voice, native phone shells, a status feed
   for other bars and launcher actions cannot honestly have three surfaces. A second waiver class
   — "the surface is the device" — would let them exist.
6. **Reopen orchestration as a milestone,** with the `new` R-ORC rows triaged into it, and correct
   the rows marked `new` that are largely built and the one marked built that is not.
7. **Chat depth.** More chat-only features (attachments, memory, cross-machine merge), or hold
   chat where it is and spend the hours on the attention layer?
8. **Field proof before more platform depth.** A week of real macOS, phone, Codex and Gemini use
   before further Windows work?
9. **Split SPEC and archive done ROADMAP items?** It changes how every agent is told to work.
